# AGENTS.md

Orientation for agents working in **this repo**. It covers what lives here and
how to run it. The Simspace **format** — `simulator.yaml`, `labspace.yaml`,
slides, milestones — is not documented here on purpose; see
[Where the format reference lives](#where-the-format-reference-lives) below.

## What this repo is

A repo of one or more **entries**. Each is plain data — Markdown plus YAML — in
its own directory under `labs/`. The app that runs them is a prebuilt image
(`dockersamples/simspace`); you never touch app source, and there's no build step
for content. The app reads a `labs.json` catalog: with **one entry** it opens
directly (no landing page, no id in the URL); with **several** it shows a
selection page and runs each under `#/labs/<id>/`.

There are two kinds of entry, set by `kind:` in `labspace.yaml`:

- **a lab** (the default) — instructions on the left, a simulated terminal on the
  right.
- **a slide deck** (`kind: slides`) — presentation slides, which can embed a live
  demo terminal.

A deck and its lab are usually one workshop: two directories, two cards on the
landing page, one deploy.

You **never write `labs.json`** — it's generated from each entry's
`labspace.yaml` (and regenerated by `validate`), so it can't drift. You only edit
files under `labs/`.

```
labs/
  getting-started/        # a lab — the directory name is its id
    labspace.yaml         # config: title, catalog card, terminals, files, sections
    simulator.yaml        # command behaviour: scenarios (when → then), state, controls
    *.md                  # one markdown file per section
  getting-started-slides/ # a deck (kind: slides) — optional, pairs with the lab above
    labspace.yaml         # same format + theme/brand; `slides:` instead of `sections:`
    assets/               # its own logo files (brand paths are entry-relative)
    *.md                  # one markdown file per chapter, split into slides on `---`
.sbxenv.yaml              # `sbx env run` — the sandbox that carries the authoring skills
compose.yaml              # `up dev` to preview, `run --rm validate` to check
Dockerfile                # optional: build a container that serves these entries
CLAUDE.md                 # loads this guide automatically in Claude Code
.claude/                  # pre-allowed commands + the post-edit validate hook
.github/workflows/        # validate.yml (PRs) + deploy.yml (Pages on push to main)
```

## The loop

```bash
docker compose up dev                 # live preview at http://localhost:5173
docker compose run --rm validate      # validate every entry — ALWAYS before committing
```

`validate` checks every entry under `labs/`, regenerates `labs.json`, and exits
non-zero on errors (dangling references, unmatched commands, `{{ args.X }}` with
no capture, an unknown slide `layout:`/`theme:`, or **nothing found**). Treat a
red validate as a broken repo. Edits to `labs/` show in the preview on **browser
refresh**.

Validation can't see everything: a deck's layouts are visual, so a slide that
overcrowds or a heading that wraps badly only shows up in the preview.

`up dev` also starts the optional **pulse** backend (presence + analytics), so
live "who's here" presence and the instructor insights dashboard
(`#/labs/<id>/insights`, token `dev-token`) work while you author. In production
these are enabled by setting `pulse-endpoint` in `.github/workflows/deploy.yml`;
opt a lab out with `tracking: false` in its `labspace.yaml`.

In Claude Code, a **PostToolUse hook** (`.claude/`) runs `validate` automatically
after you edit anything under `labs/` and feeds any errors back to you — so fix
them before finishing. The `docker compose` and `validate-lab` commands are
pre-allowed, so they won't prompt.

**Definition of done:** validation is green, every hands-on section has at least
one milestone (`steps:` + `completes:`), and for anything non-trivial you've
eyeballed it in `docker compose up dev`. Then commit and push to `main` → CI
validates and GitHub Pages deploys automatically. Pull requests are validated by
`.github/workflows/validate.yml` before merge.

## Where the format reference lives

**Not in this repo.** It ships in the
[`simspace-authoring-kit`](https://hub.docker.com/r/dockersamples/simspace-authoring-kit) sandbox
kit, named by [`.sbxenv.yaml`](.sbxenv.yaml) and resolved fresh every time a
sandbox is created:

```console
$ sbx env run
```

That gives you Claude Code with three skills already installed:

- **authoring-lab** — sections, `simulator.yaml` scenarios, milestones,
  terminals, controls, seed files, the `labspace.yaml` reference.
- **authoring-slidedeck** — `kind: slides`: layouts, theme, speaker notes,
  fragments, components, the in-slide demo terminal.
- **importing-slidedeck** — converting an existing PowerPoint / Keynote /
  Google Slides / PDF deck into a Simspace deck.

Keeping them out here is the point. Vendored into the repo, they froze at the
moment the repo was generated: the format gained slide decks, milestones and
output pacing, and every existing lab repo's agent stayed unaware of all of it.
Versioned with the platform, they describe today's Simspace no matter how old
this repo is.

If you are working **without** a sandbox, read the authoritative specs directly —
[`dockersamples/simspace`](https://github.com/dockersamples/simspace) →
`spec/simulator.md`, `spec/labspace.md`, `spec/catalog.md`, `spec/slidedeck.md`.
They are normative, and the skills are summaries of them.

> [!IMPORTANT]
> `---` is the slide separator. If you add a markdown formatter to this repo,
> **exclude `labs/`**: Prettier and friends rewrite `***` and `___` to `---`,
> which would silently split one slide into two. Use `----` (four or more) for a
> real horizontal rule.
